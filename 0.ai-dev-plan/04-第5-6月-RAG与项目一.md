## 一、RAG 是什么

**RAG（检索增强生成）：** 先从知识库里找到相关资料，再让大模型根据这些资料回答。这样能解决大模型"不知道你的私有数据"和"容易胡编"两个问题。

```
【离线：建索引】
文档 → 解析 → 切分成片段 → 向量化 → 存入向量数据库

【在线：回答问题】
用户问题 → (查询改写) → 检索相关片段 → (重排序) → 片段和问题拼进提示词 → 大模型生成回答 → 附上引用出处
```

括号里的步骤是优化项，先做出最简单的版本，再一步步加。

## 二、每周计划

### 第 18 周：最小可用的 RAG

| 天 | 内容 |
|---|---|
| 周一 | RAG 的概念和整体流程；向量和相似度的直觉（意思相近的句子，向量距离也近） |
| 周三 | 调用向量化（Embedding）API，计算几个句子之间的相似度，验证上面的直觉 |
| 周五 | 用 Chroma（最简单的向量数据库）存入向量并检索 |
| 周末 | **用不到 100 行代码写一个最简单的 RAG：** 读入 10 篇 Markdown 文档，按固定长度切分，存入 Chroma，提问后检索前 3 个片段，交给大模型回答 |

### 第 19 周：文档处理和切分

| 天 | 内容 |
|---|---|
| 周一 | 下载 FastAPI 官方文档（GitHub 上 `fastapi/fastapi` 仓库的 `docs/` 目录，有中文版） |
| 周三 | 切分策略：固定长度、按标题层级、递归切分、片段之间的重叠 |
| 周五 | 特殊内容：代码块不能从中间切断；表格要整体保留；元数据记录来源文件和所属标题 |
| 周末 | 实现"按 Markdown 标题切分 + 代码块保护"，和第 18 周的固定长度切分对比效果 |

### 第 20 周：向量化模型和向量数据库

| 天 | 内容 |
|---|---|
| 周一 | 向量化模型的选择：bge-m3（开源，可本地运行）、阿里云百炼的 text-embedding（API 调用）；维度、中英文支持 |
| 周三 | PostgreSQL + **pgvector**：用 Docker 启动，建表，存入向量 |
| 周五 | 向量索引的概念（HNSW），为什么不能一个个比较 |
| 周末 | 把存储从 Chroma 换成 pgvector；做成 FastAPI 服务 |

> 为什么用 pgvector：业务数据和向量放在同一个数据库里，工程上最简单，企业里也很常见。Milvus 了解概念即可，面试能说出两者的区别。

### 第 21 周：构建评测集（⚠️ 最关键的一周）

| 天 | 内容 |
|---|---|
| 周一 | 为什么要先评测再优化：没有评测，就不知道改动到底有没有用 |
| 周三 | 写评测题（方法见下文"评测集设计"） |
| 周五 | 继续写评测题；写评测脚本，自动计算检索召回率 |
| 周末 | 写完评测题；跑出**基线**（当前版本的分数），记进实验记录表 |

### 第 22 周：检索优化

| 天 | 内容 |
|---|---|
| 周一 | **混合检索**：关键词检索（BM25，中文要先用 jieba 分词）加向量检索 |
| 周三 | 结果融合：RRF 算法（按排名融合，不用统一两种分数的量纲） |
| 周五 | **重排序**：先粗召回 20 条，再用重排序模型（如 bge-reranker）精选出前 5 条 |
| 周末 | 依次加入混合检索、重排序，每加一步跑一次评测，记录分数变化 |

### 第 23 周：生成优化

| 天 | 内容 |
|---|---|
| 周一 | 提示词：要求只根据给定资料回答，并标注引用的是哪个片段 |
| 周三 | **拒答**：资料里没有答案时，回答"文档中没有找到"，而不是胡编 |
| 周五 | 多轮对话：对追问做**查询改写**。比如"那它怎么用？"，要结合历史改写成完整的问题再去检索 |
| 周末 | 加上 LLM-as-Judge（用大模型给回答打分）评测回答质量，人工抽查 20% 校验它判得准不准 |

## 三、项目一详细设计

### 功能清单

| 优先级 | 功能 |
|---|---|
| 必做 | 基于文档的问答，流式输出 |
| 必做 | 每个回答附带引用出处（文件名、章节标题、原文片段） |
| 必做 | 文档里没有答案时拒绝回答 |
| 必做 | 混合检索 + 重排序 |
| 必做 | 评测集 + 自动评测脚本 + 实验记录 |
| 必做 | 多轮对话（查询改写） |
| 加分 | 多个文档来源，可以按来源筛选 |
| 加分 | 增量更新：文档变化时只重建变化的部分（用文件哈希判断） |
| 加分 | 用 Langfuse 记录每次问答的检索结果、耗时、成本 |

### 技术栈

| 层 | 选型 |
|---|---|
| 后端 | FastAPI |
| 数据库 | PostgreSQL + pgvector |
| 缓存和会话 | Redis |
| 向量化 | bge-m3 或百炼 text-embedding |
| 关键词检索 | BM25 + jieba |
| 重排序 | bge-reranker 或百炼的 rerank API |
| 大模型 | DeepSeek 或通义千问 |
| 前端 | Streamlit 或 Gradio |
| 部署 | Docker Compose + 云服务器 |

### 评测集设计

**数量：** 60–100 题。

**题型分布：**

| 题型 | 占比 | 例子 |
|---|---|---|
| 事实型 | 30% | FastAPI 中怎么声明一个可选的查询参数？ |
| 操作型 | 25% | 怎么给 FastAPI 接口加上 JWT 认证？ |
| 对比型 | 15% | `Path` 和 `Query` 有什么区别？ |
| 多跳型 | 15% | 答案分散在两篇不同的文档里 |
| 无答案型 | 15% | 问文档里根本没有的内容，正确行为是拒答 |

**每道题的格式**（一行一个 JSON）：

```json
{"id": 1, "question": "...", "answer": "参考答案", "sources": ["docs/zh/tutorial/query-params.md"], "type": "事实型"}
```

**怎么写：** 可以让大模型先根据文档生成候选问题，**但必须由你逐题检查和修改**，否则评测集会偏向模型擅长的题目。无答案型和多跳型最好自己写。

### 评测指标

| 类别 | 指标 | 含义 |
|---|---|---|
| 检索 | Recall@5 | 正确的文档片段是否出现在前 5 个检索结果里 |
| 检索 | MRR | 正确片段排在第几位（越靠前越好） |
| 生成 | 回答正确率 | 由 LLM-as-Judge 打分，人工抽查校准 |
| 生成 | 引用准确率 | 标注的出处是否真的包含答案 |
| 生成 | 拒答准确率 | 无答案的题有没有正确拒答，有答案的题有没有误拒 |
| 性能 | 延迟 | P50、P95 响应时间 |
| 成本 | 单次问答成本 | 平均每次问答花多少钱 |

## 四、面试会被问的问题

1. 你的切分策略是什么？为什么这么选？试过别的吗？
2. 为什么要混合检索？只用向量检索有什么问题？（提示：专有名词、函数名、错误码这类精确匹配，向量检索容易漏）
3. RRF 的原理是什么？为什么不直接把两个分数加起来？
4. 重排序为什么能提升效果？它和向量检索有什么本质区别？（提示：双塔模型 vs 交叉编码器）
5. 你的评测集是怎么构建的？怎么保证它的质量？
6. LLM-as-Judge 可靠吗？你怎么验证的？
7. 怎么减少幻觉？
8. 文档更新了怎么办？
9. 如果文档量扩大 100 倍，哪里会先出问题？怎么解决？
10. 延迟主要花在哪个环节？怎么优化？
