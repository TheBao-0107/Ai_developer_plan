## 二、为什么选这个方向

### 选它的理由

1. **覆盖面广，退路多。** 检索（RAG）本来就是 Agent 调用的一个工具，学 Agent 一定会学 RAG，反过来不成立。找工作时 Agent 岗、RAG 岗、普通 AI 应用岗都能投。
2. **偏工程，不偏算法。** Agent 的难点是状态管理、并发、沙箱、错误恢复、权限控制、可观测性，这些都是软件工程问题。RAG 优化到后期要调向量化模型、训练重排序模型，会往算法靠。我喜欢写代码，又明确不走算法，所以 Agent 方向更合适。
3. **平台替代不了。** 简单的知识库问答，用阿里云百炼、Dify 点几下就能搭出来，这类岗位价值在下降。能自主完成多步任务的 Agent 需要真正的工程能力，需求在增长。
4. **和过去的经历有连接。** 调试 Agent，就是看一条多步执行的轨迹（Trace），找出哪一步错了。这和我做过的抓日志、分析 Trace 是同一种能力。

### 风险

- **技术变化快：** 框架一两年就换一批。**对策：** 先手写 Agent，学原理，不死记某个框架。
- **岗位标题有水分：** 很多"Agent 开发"岗位其实是用 Coze 拖工作流。**对策：** 看 JD 的具体内容，判断方法见 `09-求职策略.md`。
- **真正的 Agent 岗门槛略高：** **对策：** 第一份工作是 RAG 或普通 AI 应用开发岗也完全可以接受，进去以后再往 Agent 做。**不要只投标题带"Agent"的岗位。**

## 五、三条规则

1. **每个月底对照检验标准自查。没达标就延长，不要跳过。** 后端基础不牢，后面写项目会很痛苦。延后一两周完全没关系，整体计划留有余量。
2. **每周至少往 GitHub 提交一次代码。** 既是进度记录，也是面试时的证明。
3. **某一周没学成很正常，下周接着来。** 真正要避免的是因此放弃。
